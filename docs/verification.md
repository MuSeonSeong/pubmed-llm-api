## 최종 검토 수정

새 리뷰어가 전체 구현을 검토했습니다. 샤드 인덱스가 없는 모델을 준비 완료로 판단하던 문제를 수정했습니다. 실제 모델 파일에 의존하던 MPS 로딩 단위 테스트도 독립 fixture로 바꿨습니다. 두 문제 모두 수정 전 실패와 수정 후 통과를 확인했습니다. 남긴 미수정 검토 항목은 없습니다.

최종 Docker 이미지를 다시 빌드해 HTTP 채팅을 확인했습니다. Qwen3-0.6B CPU에서 2+2=4 응답을 받았으며 HTTP 200, 첫 로드 포함 약 9.4초였습니다. 테스트 컨테이너와 네트워크는 정리했습니다.

## 구현 판단과 영향

1. 승인받은 새 프로젝트의 main에서 직접 작업했습니다. 별도 저장소가 원래 프로젝트와 격리됩니다. 나중에 별도 작업 브랜치가 필요하면 구현 커밋을 옮겨야 합니다.
2. MPS는 CPU에서 로딩한 뒤 MPS로 옮깁니다. 설치된 Torch/Transformers에서 직접 MPS 로딩은 충돌했고 CPU 경유 방식은 실제 실행에 성공했습니다. 일시적인 CPU 메모리와 로딩 시간이 추가됩니다.
3. Qwen3 JSON 및 Qwen3.5 공식 XML 도구 호출을 모두 지원합니다. 공식 템플릿과 실제 생성 결과에 맞춘 결정입니다. 이후 템플릿이 바뀌어 지원하지 않는 형식이 나오면 HTTP 502로 실패합니다.
4. Windows 및 CUDA 실장비 실행은 검증하지 못했습니다. 이식 가능한 소스와 설치 명령은 제공했으며 해당 하드웨어에서 추가 수정이 필요할 수 있습니다.

## 서버 저장과 계정 — 2026-10-09

대화를 이 프로젝트의 서버에 계정별로 저장하고, 이 PC를 친구들이 인터넷으로 쓰는 서버로 만들었습니다. 사용법은 README의 "대화 저장 API"와 "서버 PC로 배포하기", 그리고 [deploy.md](deploy.md)를 참조합니다. 저장소로 Redis 대신 SQLite를 고른 이유도 deploy.md에 있습니다.

### 추가한 기능

- **서버**
  - `data/chat.db`(SQLite, WAL)에 계정·세션·대화·설정, `data/files/`에 첨부 이미지. `data/`는 Git에서 제외
  - 대화마다 rev, 변경마다 전역 seq, 삭제 기록(tombstone)으로 여러 기기 동기화
  - scrypt 비밀번호, 로그인 시도 제한, HttpOnly 세션 쿠키, CSP 등 보안 헤더, 계정별 저장 용량 제한
  - 답변 중인 대화(`live`) 표시, 계정당 동시 답변 2개, 15초마다 `: ping`
- **웹 UI**
  - 로그인 화면. 브라우저는 계정별 사본(캐시)만 두고 서버와 동기화
  - 첨부 이미지 업로드, 서버 저장 전 기록 한 번 가져오기, 다른 기기에서 답변 중인 대화는 읽기 전용
- **배포**
  - `scripts/users.py`(계정 관리), `scripts/serve.py`(계정 모드, 127.0.0.1, 잠자기 방지)
  - macOS LaunchAgent 설치·해제 스크립트, Cloudflare Tunnel 설정 예시

### 검증 방식

- pytest 292개, `node --test` 90개(`tests/chat.test.mjs`, `tests/sync.test.mjs`)가 통과했습니다.
- 빈 `DATA_DIR`로 실제 `scripts/serve.py`를 계정 모드로 실행해 확인했습니다(포트 8771, Qwen3-0.6B MPS).
  - CLI 15개 항목: 계정이 없거나 `AUTH_ENABLED=false`면 시작하지 않음, 한글 이름 계정 만들기, 예약 이름·짧은 비밀번호 거절
  - curl 78개 항목: 로그인 전 `/`→`/login`, `/docs` 404, API 401, 쿠키 속성(https 프록시 뒤에서 `Secure`), 대화의 seq·409·410·삭제 기록, 설정, 업로드 형식 판별, 다른 계정의 파일 404, 스트리밍 중 `live`와 세 번째 요청 429 `busy`, Qwen3-0.6B에 이미지 422 `vision_unsupported`(2B는 불러오지 않음), 로그인 시도 제한, 로그아웃
  - 웹 UI 모듈(ChatStore, RemoteSync)을 Node에서 실제 서버에 연결해 23개 항목: 두 기기 동기화, 다른 기기의 답변을 읽기 전용으로 지켜보다 최종 답 받기, 409·410 처리, 업로드, 예전 기록 가져오기
  - 헤드리스 Chrome 20개 항목: 로그인(Enter)·로그아웃, 동기화 상태 표시, 이미지 첨부 미리보기, 빈 계정에 예전 기록 제안, CSP 위반과 콘솔 오류 없음
  - 실행 중에는 `caffeinate`가 서버 프로세스를 대신해 잠자기를 막고, 종료하면 풀림

### 통합하며 고친 점

- 스크립트가 실행되기 전에 로그인 폼에서 Enter를 누르면, 브라우저가 폼을 GET으로 보내 비밀번호가 주소창·방문 기록·접속 로그(`data/logs/access.log`)에 남을 수 있었습니다. 폼을 POST로 바꾸고, 로그인 버튼은 스크립트가 켤 때까지 비활성으로 둡니다.
- 문서에 로컬 모드 대화를 계정으로 옮기는 `users.py adopt-local`을 추가했습니다. 정적 파일의 `no-cache`에 맞게 Cloudflare 캐시 안내를 고치고, 복원할 때 `data/` 권한(700)을 지키게 했습니다.

### 남은 제한

- 로그인 시도 제한, `live` 표시, 동시 답변 수는 메모리에 있어 서버 프로세스(워커) 1개를 전제로 하며 재시작하면 초기화됩니다. `scripts/serve.py`는 워커 1개로 실행합니다.
- Cloudflare Tunnel·Tailscale Funnel을 통한 실제 인터넷 접속과 LaunchAgent 실제 등록은 실행하지 않았습니다. 설정 파일 검증과 `--dry-run`, 임시 명령으로 바꾼 설치 시험만 했습니다.
- Docker 이미지는 다시 빌드하지 않았습니다.

## MLX 런타임, 모델 선택, 추론 단계 — 2026-10-10

Transformers로 돌리던 Qwen3.5-2B·Qwen3-0.6B는 실제로 쓰기에 약하고 느렸습니다(2B 프롬프트 읽기 초당 약 1000토큰, 모델 전환마다 2~5초). 이 맥북 에어 M5(16 GB)에서 측정해 mlx-vlm 0.7.6의 `mlx_vlm.server`로 돌리는 MLX 4비트 모델(Qwen3.5 9B·4B)을 골랐습니다. 사용법은 README의 "모델 고르기"와 "MLX 런타임", 배포는 [deploy.md](deploy.md)를 참조합니다.

### 추가한 기능 (서버)

- 모델마다 사이드카 프로세스 하나(`app/mlx_runtime.py`, 감싸는 프로그램 `app/mlx_sidecar.py`)
  - TCP 포트 없이 Unix 소켓 `<폴더>/<n>.sock`에서만 응답. 폴더는 앱 실행마다 `tempfile.mkdtemp`로 만드는 권한 700 폴더(경로가 AF_UNIX 한도 104바이트를 넘으면 `/tmp` 아래)이고 앱이 끝나면 지웁니다. 감싸는 프로그램은 `MLX_SIDECAR_SOCKET`이 없으면 시작하지 않습니다. 시작할 때마다 새 키(환경 변수로만 전달), 자기 프로세스 그룹
  - 상태: `missing`·`stopped`·`starting`·`ready`·`failed`(이유 포함)
  - `/health` 확인 → 한 토큰짜리 데우기 → 토큰 세는 토크나이저 → 준비. 로컬 모드는 준비 뒤(재시작 뒤에도) 백그라운드에서 PubMed 지시문·도구 설명을 캐시(PubMed는 10초까지만 기다림)
  - 시작은 앱 수명 동안 풀이 맡음: 기다리던 요청이 떠나도 시작은 계속되고, 같은 모델을 기다리는 요청은 한 번의 시작을 함께 기다리며 실패하면 각자 그 시작의 오류(`model_missing`, `model_unavailable`과 이유)를 받습니다. 앱이 끝나면 진행 중인 시작을 취소하고 그 프로세스를 멈춥니다
  - 죽으면 다음 요청 때 재시작, 종료 시 SIGTERM → 10초 → SIGKILL, 앱이 사라지면 스스로 종료
- `MODELS`(기본: Apple Silicon은 MLX 모델, 그 밖은 Transformers 모델), `PRELOAD_MODELS`(이후 `default`·`all`·`none`으로 바뀜, 아래 "기본 모델만 상주"), `KV_CACHE_GB`(기본 0: 접두 캐시는 메모리에만), `MLX_CHECKPOINT_INTERVAL`(512)·`MLX_CHECKPOINT_ENTRIES`(8)
- 중지: 0.1초마다 확인해, 첫 토큰이 오기 전(긴 프롬프트를 읽는 중)이라도 스트림을 닫고 지금까지의 글과 `cancelled`를 돌려줍니다
- `/v1/models`: 켜진 모델만, 이름·특징·이미지·추론·생각 단계·문맥 한도·상태. `/health`의 `inference.models`
- 요청: `reasoning_effort`(none/light/medium/high/max = 생각 0/512/2048/4096/8192토큰), `max_tokens`는 답변 길이(최대 4096), `temperature` 생략 시 모델 권장값, `model` 생략 시 기본 모델, 예전 `thinking: true`는 medium
- Transformers 경로도 같은 생각 예산을 쓰고, 답변 길이를 먼저 지킨 뒤 남는 문맥만큼만 생각합니다(마무리 문구는 그대로)
- 한국어 질문에 한자·가나 막기: 사이드카가 그런 글자를 쓰는 토큰(약 5만 9천 개)을 logits에서 −∞로 막습니다(생각 포함). 마지막 질문에 한글이 있고, 어느 사용자 메시지에도 한자·가나가 없고, 어느 사용자 메시지와 시스템 지시문도 그런 글을 요청하지 않을 때만(일본어·중국어·한자·한문·간체·번체·히라가나·가타카나, Japanese·Chinese·Mandarin·Cantonese·kanji·hanja·hanzi·hiragana·katakana) 막습니다. 요청은 무엇으로 쓸지를 말하는 표현만입니다: 글자 이름 바로 뒤의 "로/으로"나 "번역·표기·병기·발음·읽는 법·뜻·단어·글자·표현·인사·이름·원문·버전", 영어의 "in/into/to Japanese·Chinese", "translate … Chinese", "Japanese:", kanji·hanja·hanzi·hiragana·katakana·pinyin. 그 동사를 바로 부정하면("한자로 쓰지 마세요", 앞의 not·never·don't·avoid·no, 단 "but"이 뒤집으면 요청) 요청이 아니고, 그저 언급한 말("중국어 논문은 빼고", "한자나 중국어를 섞지 마세요")과 "한자리"·"한자세"·"한문장"·"시간체크"·"한자녀"처럼 글자만 같은 낱말, 첨부 파일 내용(`[첨부 파일: …]` 코드 블록)은 요청으로 치지 않습니다. 긴 메시지는 앞뒤 4천 자만 읽고(한자·가나 확인은 2만 자) 작업 스레드에서 판단하므로, 60 MB 메시지도 0.02초에 끝납니다
- 시각 제어 토큰(`<|vision_start|>` 등)은 역할과 관계없이 보내는 모든 글(시스템, 답변, 도구 호출 인자 안의 문자열, 도구 결과, PubMed 서버가 준 도구 설명)에서 한 번에 공백 하나로 바꿉니다. 어느 토큰에도 공백이 없으므로 바꾼 자리 양옆이 이어져 새 토큰이 생기지 않습니다. 하나라도 남으면 mlx-vlm의 공용 GPU 루프가 실패해 함께 생성 중이던 모든 답변이 끊깁니다
- 계정 모드에서는 `X-APC-Tenant: user-<id>-<계정을 만든 시각>`으로 계정마다 접두 캐시를 나누고(지운 계정의 ID를 새 계정이 받아도 겹치지 않음), 사이드카에 `MLX_SIDECAR_PRIVATE=1`을 주어 이미지 특징 캐시를 끕니다(`ResponseGenerator(vision_cache=None)`)
- 새 오류 코드 `model_unavailable`(503). PubMed 지시문에 "사용자가 쓴 언어로 답하라"는 문장 추가
- `prepare_models.py`는 켜질 모델만 받고, `--model`(여러 번)·`--all`로 다른 모델도 받습니다

  - 시작 소유: 재시작을 기다리던 요청이 취소돼도 시작이 끝나 ready가 되고 PubMed 프롬프트도 다시 캐시되는지, 동시에 기다린 요청 세 개가 한 번의 시작을 공유하고 실패하면 각자 다른 오류 객체를 받는지, 앱 종료가 진행 중인 시작을 취소해 SIGTERM하고 기다리던 요청이 `model_unavailable`을 받는지, `run()` 없이 호출한 쪽이 맡은 시작은 취소되면 멈추는지

  - 생성: 생각을 `<think>…</think>`로 합친 원문, 도구 호출 표기 그대로 전달(`tool_parser: longcat`), 생각 안의 도구 호출을 답변으로 옮김, 서버가 파싱한 호출을 표기로 되돌림, 취소 시 스트림 닫기, 아무것도 오지 않는 스트림(긴 프롬프트 읽기)에서 0.2초 뒤 중지하면 2초 안에 `cancelled`, 400 → 413, 그 밖의 HTTP 오류와 스트림 중 오류 → 502, 연결 실패 → 한 번 재시작 → 503, 생각 예산과 `max_tokens`, 문맥이 모자랄 때의 축소, 샘플링 기본값과 temperature 지정, 계정 모드에서만 테넌트 헤더, 이어 쓰기 지시, 이미지 축소와 토큰 추정, 도구 호출 id 매칭

### mlx-vlm 0.7.6 소스에서 확인한 점과 구현 판단

1. 요청마다 넣는 logits 처리기는 생각이 끝날 때(`</think>`)까지 꺼 둡니다(JSON 문법용 `ThinkingAwareLogitsProcessor`). 그대로면 한자 마스크가 생각에는 걸리지 않으므로, 사이드카가 `ResponseGenerator._wrap_processors_until_thinking_done`도 고쳐 마스크만은 처음부터 켭니다. 두 훅 중 하나라도 없으면 사이드카가 시작하지 않습니다.
2. 요청이 `seed`를 주지 않으면 seed 0과 토큰 위치로 샘플링 키를 만들어, 같은 프롬프트에는 늘 같은 답이 나옵니다. "다시 생성"이 다른 답을 내도록 요청마다 무작위 seed를 보냅니다.
3. 너무 긴 프롬프트의 HTTP 400(`PromptTooLongError`)은 `MAX_KV_SIZE`를 정했을 때만 납니다. 정하지 않으므로 문맥 한도는 앱의 토큰 세기가 지키고, 400 → 413 변환은 안전망으로 남겼습니다.
4. 이미지 처리기는 한 장에 최대 16,777,216화소(약 1만 6천 토큰)까지 받습니다. Transformers 경로와 같은 512×512화소 이하로 줄여 PNG로 보냅니다(사양은 그대로 전달).
5. 채팅 요청마다 자동 문맥 압축이 프롬프트를 한 번 더 렌더링하고 셉니다. `context_management: []`를 보내 이 과정을 건너뛰고, 서버가 대화를 요약해 바꿀 일도 없게 했습니다.
6. 서버(uvicorn)는 모델을 다 불러온 뒤에야 소켓을 만들고, 끝날 때 소켓 파일을 지웁니다. 앱은 `/health`의 `loaded_model`이 이 앱이 띄운 모델 경로인지 봅니다. `/health`에도 API 키가 필요합니다. uvicorn은 만든 소켓의 권한을 0o666으로 바꾸므로, 다른 사용자를 막는 것은 소켓이 든 폴더의 권한(700)입니다. `mlx_vlm.server.cli`는 `uvicorn.run(app, host=…, port=…, …)`를 모듈 속성으로 부르므로, 감싸는 프로그램이 그 함수를 `uds=<소켓>`으로 부르는 함수로 바꿉니다.
7. 디스크 캐시와 압축 키의 기본 위치는 `~/.cache/mlx-vlm`입니다. `MLX_VLM_CACHE_HOME`과 `APC_DISK_PATH`를 `data/kv-cache/` 아래로 두어 대화에서 나온 데이터가 `data/` 밖에 쌓이지 않게 했습니다.
8. 스트리밍 delta는 생각을 `reasoning`과 `reasoning_content` 두 이름으로 함께 보내므로 한 번만 읽습니다.
9. 이미지 특징 캐시(`VisionFeatureCache`)는 계정이 아니라 이미지 내용(해시)으로 찾습니다. `ResponseGenerator`는 이를 `vision_cache=` 이름으로 받고, `_gpu_embed`는 `None`이면 캐시 없이 인코딩합니다.
10. 디스크 계층은 프롬프트의 토큰 ID를 safetensors 메타데이터(`token_ids`, 쉼표로 이은 숫자)에 평문으로 저장하고, 대화를 지워도 지우지 않습니다.
11. 서버의 `BatchGenerator`는 만들어질 때 `wired_limit`으로 wired 메모리 한도를 GPU 권장 작업 메모리(`max_recommended_working_set_size`)까지 올리고 닫힐 때 이전 값으로 되돌립니다(`generate/ar.py`, `generate/common.py`). 그런데 일을 마쳐도 닫지 않고 두었다가, 진행 중인 요청이 없을 때 새 요청이 오면 그제야 닫고 바로 새로 만듭니다(`server/generation.py`). 그래서 첫 요청(데우기) 뒤에는 쉬는 동안에도 한도가 권장 작업 메모리로 잡혀 있고, 사이드카가 시작할 때 정한 한도는 요청 사이에 아무 역할도 하지 않습니다.

### 남은 제한

- 이 작업 동안 같은 맥에서 모델 벤치마크가 GPU를 쓰고 있어 실제 사이드카를 띄우거나 MLX 모델을 불러오지 않았습니다(재검토 때 잰, 쉬고 난 뒤의 첫 토큰 시간은 예외). 실제 모델로는 나중에 따로 확인했습니다(아래 "실제 모델로 확인한 결과"와, 아직 확인하지 않은 항목).
- MLX 모델의 이어 쓰기는 "이어서 쓰라"는 지시 메시지로 받기 때문에 이어 붙는 곳의 공백이 원래와 다를 수 있습니다.
- 웹 UI(입력창의 모델 버튼, 추론 단계 메뉴 등)는 같은 사양으로 따로 구현하며 이 절에는 포함하지 않았습니다.

**바꾼 것**

- `PRELOAD_MODELS`: `default`(새 기본값: 기본 모델이 MLX 모델이면 그것만)·`all`·`none`. 예전 불리언도 받습니다(`true`·`1`·`yes`·`on` → `all`, `false`·`0`·`no`·`off` → `none`). 어떤 모델을 미리 불러올지는 `ModelManager.preload_ids()`가 정합니다.
- `MLX_IDLE_MINUTES`(기본 10, 0이면 끄지 않음): 미리 불러오지 않은 MLX 모델이 이 시간 동안 요청을 받지 않으면 사이드카를 끕니다. `all`이면 끌 모델이 없고 `none`이면 기본 모델도 끕니다.
- `MLXPool.run(prefix, preload_ids)`는 그 모델만 기본 모델부터 시작하고, 같은 작업 그룹에서 30초마다 쉬는 모델을 확인합니다. 사이드카마다 처리 중인 요청 수와 마지막 요청이 시작하거나 끝난 시각(새로 띄운 뒤에는 ready가 된 시각)을 두고, ready이고 처리 중인 요청도 진행 중인 시작도 없으며 미리 불러온 모델이 아니고 한도보다 오래 쉰 사이드카만 작업 스레드에서 끕니다(SIGTERM → 기다림 → SIGKILL). 상태는 `stopped`, 로그는 `stopped <모델> after N min idle`이고, 다음 질문은 `ensure()`로 다시 띄웁니다.
- 요청은 모델을 기다리기 시작할 때부터(`ensure()` 전) 스트림이 끝날 때까지 처리 중으로 칩니다. 그래서 `ensure()`가 ready를 확인한 뒤 스트림을 열기 전에 꺼지는 일이 없습니다(스트림 중에 꺼지면 Unreachable 재시도로도 되살릴 수 없음). 잠금(lock)을 잡는 동안 다른 작업이 돌 수 있으므로 잠금을 잡은 뒤 조건을 다시 확인합니다.
- 시작과 끄기는 사이드카마다 한 번에 하나만 합니다(같은 잠금). 새 사이드카는 같은 소켓 경로에서 듣는데 이전 프로세스는 끝날 때 그 소켓 파일을 지우므로, 끄는 중에 온 질문은 이전 프로세스가 끝난 뒤에 새로 띄웁니다.
- 웹 화면은 바꿀 것이 없었습니다. 끈 모델은 메뉴에서 그대로 고를 수 있고 "첫 질문 때 불러와요"로, 서버 상태 툴팁에는 "대기 중 · 첫 질문 때 불러와요"로 보입니다. 서버 표시는 기본 모델의 상태만 보므로 초록색 그대로이고, 그 모델을 다시 띄우는 동안만 "모델 준비 중"입니다. `node --test`의 서버 표시 검사에 이 경우를 분명히 적었습니다.

- `MLX_SIDECAR_SOCKET` 없이 `python -m app.mlx_sidecar`를 실행하면 바로 끝나는지(가짜 mlx_vlm 모듈로만 확인)
- 사이드카를 `kill -9`로 죽인 뒤 질문하고 바로 창을 닫아도 모델이 ready가 되는지
- 첫 PubMed 질문의 `cached_tokens`(시작할 때 PubMed 프롬프트를 캐시하는 것은 확인), PubMed가 꺼져 있어도 모델이 바로 ready가 되는지
- `block_cjk`: "이 초록을 일본어로 번역해 줘"와 그 후속 질문("조금 더 자연스럽게 다듬어 줘")에 가나가 나오는지, "한자나 중국어를 섞지 마세요"라는 맞춤 지시문에서도 한자가 섞이지 않는지(보통 한국어 질문은 위에서 확인)
- 계정 모드: 두 계정이 같은 프롬프트를 보낼 때 서로의 캐시를 쓰지 않는지(`cached_tokens`), 같은 이미지를 두 번 보내도 이미지 특징 캐시를 쓰지 않는지
- 시스템 지시문이나 도구 결과에 `<|vision_start|><|video_pad|>`가 든 요청이 다른 사람의 답변을 끊지 않는지
- `KV_CACHE_GB=4`이면 `data/kv-cache/<모델>/` 아래에 파일이 생기고, 기본값에서는 생기지 않는지
